### 2. Section snap — "one scroll gesture, one section", desktop only
`components/Services/useSectionSnap.js` (new) + a `Section 7` SCSS group + page wiring.

**Approach: thin JS layer over native CSS scroll-snap, not a scroll hijacker.** The user asked for
"whatever is smooth and reliable". A full preventDefault-everything jack would mean re-implementing
keyboard, touch, momentum, the scrollbar and accessibility by hand, and each of those is a way for
the page to turn hostile. So: `scroll-snap-type: y proximity` does the work, and the hook only
intercepts `wheel` to add the discrete feel.

**`proximity`, never `mandatory`** — `.wsv-plans` is ~1008px against a ~900px viewport, and mandatory
would drag the reader back to its top mid-section.

**"Scroll through, then jump"** (the user's choice): a gesture is ignored while the current section
still has unseen content below (or above, scrolling up), so tall sections stay fully reachable. Past
either end of the list the browser takes over, so scrolling up off the hero and down into the footer
both feel like ordinary page scroll. The footer is deliberately not a stop.

**14 stops:** hero wrapper → `.wsv-projects` → `.wsv-nav` → `.wsv-about` → `.wsv-plans` → 9 wireframe
blocks (3 areas x 3). `SNAP_SELECTOR` in the hook is the single definition; the hook tags matches
with `.wsv-snap` at runtime so the stylesheet knows only one class and the two cannot drift. Only the
two inline cases (hero wrapper, wireframe `<section>`s) needed a marker class — every
component-owned section is matched by the class it already had, so none of them were edited.

**Four things in this codebase it had to cooperate with, all found before writing a line:**
1. `bootstrap.min.css:5` already sets `:root { scroll-behavior: smooth }` (gated on
   `prefers-reduced-motion: no-preference`). Our `window.scrollTo` therefore animates for free, and
   its duration belongs to the browser — hence a scroll-settle detector rather than a guessed
   timeout.
2. `.navbar-area` is fixed and **changes height** with `.is-sticky` (20px→15px padding at
   scrollY>150). The CSS snap position and the JS jump target must use the same number or the
   browser re-snaps ~10px after every jump. A `ResizeObserver` on the navbar keeps `--wsv-nav-h` in
   sync and both sides read only that.
3. `CoverflowCarousel` already claims ArrowLeft/ArrowRight with `preventDefault`. The hook binds the
   wheel only and leaves every key alone.
4. The SideRail's own `scrollTo` — the hook returns `markProgrammatic()`, which the page's
   `scrollTo` now calls before scrolling, so the two never steer at once.

`scroll-snap-type` has to live on `<html>`, which is shared by every route, so the rule is gated
behind an `html.wsv-snapping` class the hook adds on mount and removes on unmount. Without that this
would silently change scrolling site-wide.

**Gating:** `(min-width: 992px)` — the same breakpoint `.wsv-rail` uses to hide, so the rail and the
snapping appear and disappear together. Off entirely under `prefers-reduced-motion`, in both the JS
and a belt-and-braces CSS rule.

### Known, not fixed (out of scope — `components/Layouts/**` is Manager-gated)
`components/Layouts/Navbar.js:22-31` adds a `document` scroll listener **on every render**, with no
dependency array and no cleanup — listeners accumulate for the life of the page.
`components/Shared/GoTop.js:11-35` has the same shape. Neither is caused by this change, but both
now share the page with a wheel handler and are worth a task.

(compositor-only) and that is a one-rule swap.

## /services — smooth "sliding" scroll added (replacing the removed snap)

`components/Services/useSmoothScroll.js` (new) + an `html.wsv-smooth` rule.

**No new dependency.** Lenis/Locomotive would each have been an option, but this repo only takes new
deps on the user's explicit call (GSAP is still absent; `animejs` was added that way), and every
constraint here was already known from building the snap mechanism. ~170 lines, no install.

**Drives the real document scroll, not a wrapper transform.** This is the whole design decision.
The Locomotive-style approach translates a wrapper, which makes that wrapper the containing block
for every `position: fixed` descendant — it would tear `.navbar-area`, `.wsv-rail` and
`.wsv-progress` off the viewport. Interpolating `window.scrollTo` instead keeps fixed elements, the
native scrollbar, find-in-page and scroll anchoring all working, and anything listening to `scroll`
(ScrollProgress, the page's own scroll-spy) updates for free with no wiring.

**Wheel only.** Keyboard, scrollbar dragging and touch stay native — touch already has its own
momentum, and re-implementing the other two is exactly how this kind of thing turns hostile. Also
means no conflict with `CoverflowCarousel`, which claims Arrow keys and captures pointer events.

**`html.wsv-smooth` is load-bearing, not cosmetic.** `bootstrap.min.css` sets
`:root { scroll-behavior: smooth }`, which makes every `scrollTo` animate — including the ~60/sec
the interpolation loop issues, so each frame would start its own animation toward the next
interpolated position. Animation inside an animation; reads as sludge. The class (added on mount,
removed on unmount, so the override never leaks to other routes) switches it to `auto`, and each
step also passes `behavior: "instant"` as a second guard.

**Resync on foreign scroll:** an `owns` flag distinguishes our own `scrollTo` from a scroll the user
caused another way (scrollbar drag, keyboard, anchor jump, browser position restore); those reset
the target so the next wheel gesture continues from where the page actually is rather than snapping
back.

**SideRail now routes through `scrollToY`** rather than `scrollTo({behavior:"smooth"})` — since the
hook disables CSS smooth scrolling, the old call would have landed instantly. Its jumps now share
the same easing.

`deltaMode` is normalised (1 = lines ×16, 2 = pages × viewport height) — a line-mode mouse, common
on Windows, would otherwise crawl a few pixels per notch. Off entirely under `prefers-reduced-motion`.
Tunables at the top: `EASE` 0.09 (lower = longer glide), `ARRIVED` 0.4.

leftovers; `/`, `/lab/sections/` and `/services/hosting-services/` all 200 (the `wsv-smooth`

### Bugfix — smooth scroll did nothing on first attempt

**Cause: `scroll` events are asynchronous.** The first version guarded its own writes with a
boolean — `owns = true; window.scrollTo(...); owns = false;` — and had `onScroll` bail when `owns`
was set. But the scroll event does not fire synchronously during `scrollTo`; it is dispatched later,
by which time `owns` is already back to `false`. So every frame of the rAF loop looked like a
foreign scroll: `onScroll` reset `target` to the current position and called `stop()`. Net effect,
one wheel notch moved ~9% of a step and the loop died immediately.

**Fix:** compare positions instead of using a flag. `write()` records what it last wrote to
`wrote.current`, and `onScroll` treats the scroll as ours when `|window.scrollY - wrote.current| < 3`.
The tolerance absorbs sub-pixel rounding and the one-frame lag between a write and its event, while
a scrollbar drag or keyboard scroll lands far outside it and correctly resyncs.

Worth remembering generally: **any "is this my own scroll?" guard in this codebase has to be
position-based, not flag-based.** The same trap would apply to a future scroll-linked effect.

Verified in the SERVED dev bundle (not just on disk):
`Math.abs(window.scrollY - wrote.current) < 3`, `wrote.current = y`, `deltaMode === 1` and
`behavior: "instant"` all present. `/services/`, `/` and `/lab/sections/` all 200.

**Also cleared up:** the `G:` path used earlier in this session was a temporary mapped drive that no

## Area-to-area snapping restored — folded INTO the smooth-scroll hook, not alongside it

User: halve the spacing, and bring back the scroll mechanism but only for area-to-area crossings.

### Spacing
`$wsv-gap-area` `clamp(440px,54vw,900px)` → `clamp(220px,27vw,450px)`, and the companion `+300px` →
`+150px`. Both the `.wsv-area` and `.wsv-nav` rules read the same token, so the intro→area-2 gap and
every area→area gap halved together (~1200px → ~600px).

### Why the old hook was NOT restored from the archive
`useSectionSnap.js` had its own `wheel` listener that called `preventDefault` and drove
`window.scrollTo`. `useSmoothScroll.js` now does exactly the same. Running both would put two
handlers on one gesture, each steering the scroll — the identical class of bug as the earlier
snap-vs-CSS-snap fight that showed up as jitter.

Instead the jump is now a *case* inside the existing hook: the lerp already animates toward a
target, so an area jump is just setting that target to the next area's aligned position rather than
`target += delta`. One wheel handler, one animation loop, no arbitration needed. The archive at
`drafts/scroll-snap-mechanism.md` is kept as history but is now superseded — a restore from it
would reintroduce the conflict.

### Behaviour
`SNAP_SELECTOR = ".wsv-snap-stop, .wsv-area"` — five stops: the intro block plus the four service
areas. Inside a stop, ordinary glide. At a stop's edge, the next gesture animates to the next area.
Past either end it hands back to ordinary scrolling so the footer and the top of the page stay
reachable.

**The intro is now wrapped as one stop** (`.wsv-snap-stop` + `data-area="intro"`) in
`pages/services/index.js`. Previously hero/carousel/navigator were three separate stops; the user
counts that whole block as area 1, so crossing out of it must be one gesture, not three.

**Measured against `target.current`, not `window.scrollY`** — the glide means the real position lags
the target by design, so testing "have we reached the end of this area" against the live position
would fire the jump early and repeatedly within a single gesture. This is the same lag trap as the
earlier async-scroll-event bug, in a different guise.

Short areas centre in the readable band; a taller-than-viewport area pins under the navbar, since
centring something that overflows would push its own heading off the top. `navOffset` is measured
per use because the navbar changes height with `.is-sticky`.

Jumping is gated to `min-width: 992px` (matching `.wsv-rail`) and off under reduced motion; the
glide itself stays on at any width.

never on a page wrapper, since `filter` would make it the containing block for `position: fixed`
and tear the navbar, rail and progress bar off the viewport.

### Crossing now has to be earned — resistance instead of a hair trigger

User: "make the user do much more effort to apply the mechanism… it just flies after I touch the
scroll wheel… make the user comfortable while reading and seeing the content."

**The flaw:** reaching the arm point was itself the trigger. Once past it, the very next wheel event
— any event over `MIN_DELTA` (4px), i.e. the smallest flick — threw the reader into the next area.
There was no notion of intent, so simply reading to the end of a section launched you out of it.

**Now:** reaching the arm point only makes a crossing *possible*. Releasing it requires
`PUSH_REQUIRED` (620px) of accumulated wheel travel spent pushing at that boundary — roughly six
mouse notches. Tracked in `push` / `pushDir` / `pushAt`.

The effort resets on anything that means "not pushing any more":
- direction change (changed their mind)
- `PUSH_IDLE_MS` (600ms) without a wheel event — someone who paused to READ must not have that
  earlier scrolling counted toward a crossing; this is the part that makes it comfortable to sit and
  read at a boundary
- scrolling freely back inside the area
- a foreign scroll (scrollbar drag, keyboard, anchor jump)
- the mechanism being switched off

**While the push is building the page creeps at `PUSH_RESIST` (0.12) rather than freezing.** A hard
stop reads as a broken scrollbar and is the usual reason scroll-jacking feels hostile; heavy damping
reads as resistance and invites the extra push instead.

Tuning knobs, all named constants at the top of the file: `PUSH_REQUIRED` (how much effort),
`PUSH_IDLE_MS` (how long effort survives a pause), `PUSH_RESIST` (how much it creeps meanwhile).

Verified in the SERVED bundle: `PUSH_REQUIRED`/`PUSH_IDLE_MS`/`PUSH_RESIST`/`pushDir` and the value
620 all present. 5 snap stops intact; `/services/`, `/`, `/lab/sections/` and
`/services/hosting-services/` all 200.

## FULL design-system extraction — the portable .ds-* component layer

Correcting my own earlier under-delivery. The previous pass extracted only the `--ds-*` TOKENS
(values) and wrote a page that documented them. That is not a design system anyone can use: every
actual PATTERN — buttons, cards, splits, lists, accordions, CTAs — was still locked behind `.wsv-*`
class names that mean "web services". Another page wanting a card had to either write
`class="wsv-plan"` (a name that lies about where it belongs) or re-implement the recipe by hand.
The user pushed back on exactly this; they were right.

Inventoried all ~90 `.wsv-*` rules, separated the genuinely portable patterns from the page-specific
ones (hero, rail, progress bar, projects carousel, the e-commerce flow and consulting diagnostic
diagrams all stay with /services), and lifted the portable half into a new
`=== DESIGN SYSTEM — COMPONENT LAYER (.ds-*) ===` block at the end of `styles/style.scss`.
72 compiled rules covering:

- **typography** — `.ds-eyebrow` `.ds-h2` `.ds-h3` `.ds-p` `.ds-note`
- **layout** — `.ds-section` `.ds-band` `.ds-split` `.ds-grid-3` `.ds-grid-2` `.ds-head`
- **buttons** — `.ds-btn` (base, colourless by design) + `.ds-btn-solid` (on light) /
  `.ds-btn-light` (on dark) / `.ds-btn-block`, plus `.ds-link` / `.ds-link-light` for secondaries
- **cards** — `.ds-card`, opt-in `.ds-card-hover`, inverted `.ds-card.is-dark` (re-points its own
  heading/body/icon/list/CTA so the call site restates nothing), `.ds-card-foot`
- **parts** — `.ds-icon` / `.ds-icon-sm`, `.ds-badge`, `.ds-tag` + `.is-high/.is-mid/.is-low`
- **lists** — `.ds-list` / `.ds-list-sm`
- **media** — `.ds-frame` / `.ds-frame-media` (now also accepts `iframe` and `video`, not just `img`)
- **accordion** — `.ds-accordion` (react-accessible-accordion contract, carries the load-bearing
  `::before { display:none }` fix)
- **CTA band** — `.ds-cta`
- **switch** — `.ds-switch`
- responsive at 991/767/575 + a reduced-motion block

Everything is built on `var(--ds-*)`, so tokens remain the single source of values.

**Deliberately did NOT rename or alias `.wsv-*` onto this.** /services is the most-worked page in the
repo; re-pointing its classes mid-flight risks a regression nobody would catch quickly. The two
