### 2. Section snap — "one scroll gesture, one section", desktop only
`components/Services/useSectionSnap.js` (new) + a `Section 7` SCSS group + page wiring.

**Approach: thin JS layer over native CSS scroll-snap, not a scroll hijacker.** The user asked for
"whatever is smooth and reliable". A full preventDefault-everything jack would mean re-implementing
keyboard, touch, momentum, the scrollbar and accessibility by hand, and each of those is a way for
the page to turn hostile. So: `scroll-snap-type: y proximity` does the work, and the hook only
intercepts `wheel` to add the discrete feel.

**`proximity`, never `mandatory`** — `.wsv-plans` is ~1008px against a ~900px viewport, and mandatory
would drag the reader back to its top mid-section.

**"Scroll through, then jump"** (the user's choice): a gesture is ignored while the current section
still has unseen content below (or above, scrolling up), so tall sections stay fully reachable. Past
either end of the list the browser takes over, so scrolling up off the hero and down into the footer
both feel like ordinary page scroll. The footer is deliberately not a stop.

**14 stops:** hero wrapper → `.wsv-projects` → `.wsv-nav` → `.wsv-about` → `.wsv-plans` → 9 wireframe
blocks (3 areas x 3). `SNAP_SELECTOR` in the hook is the single definition; the hook tags matches
with `.wsv-snap` at runtime so the stylesheet knows only one class and the two cannot drift. Only the
two inline cases (hero wrapper, wireframe `<section>`s) needed a marker class — every
component-owned section is matched by the class it already had, so none of them were edited.

**Four things in this codebase it had to cooperate with, all found before writing a line:**
1. `bootstrap.min.css:5` already sets `:root { scroll-behavior: smooth }` (gated on
   `prefers-reduced-motion: no-preference`). Our `window.scrollTo` therefore animates for free, and
   its duration belongs to the browser — hence a scroll-settle detector rather than a guessed
   timeout.
2. `.navbar-area` is fixed and **changes height** with `.is-sticky` (20px→15px padding at
   scrollY>150). The CSS snap position and the JS jump target must use the same number or the
   browser re-snaps ~10px after every jump. A `ResizeObserver` on the navbar keeps `--wsv-nav-h` in
   sync and both sides read only that.
3. `CoverflowCarousel` already claims ArrowLeft/ArrowRight with `preventDefault`. The hook binds the
   wheel only and leaves every key alone.
4. The SideRail's own `scrollTo` — the hook returns `markProgrammatic()`, which the page's
   `scrollTo` now calls before scrolling, so the two never steer at once.

`scroll-snap-type` has to live on `<html>`, which is shared by every route, so the rule is gated
behind an `html.wsv-snapping` class the hook adds on mount and removes on unmount. Without that this
would silently change scrolling site-wide.

**Gating:** `(min-width: 992px)` — the same breakpoint `.wsv-rail` uses to hide, so the rail and the
snapping appear and disappear together. Off entirely under `prefers-reduced-motion`, in both the JS
and a belt-and-braces CSS rule.

### Known, not fixed (out of scope — `components/Layouts/**` is Manager-gated)
`components/Layouts/Navbar.js:22-31` adds a `document` scroll listener **on every render**, with no
dependency array and no cleanup — listeners accumulate for the life of the page.
`components/Shared/GoTop.js:11-35` has the same shape. Neither is caused by this change, but both
now share the page with a wheel handler and are worth a task.

## /services — area identity pass (nav-card shadow, area bands, jump blur, rail audit)

### 1. Rail "no highlight before area 1" — NOT a highlight bug
Traced the whole chain before touching anything, and the highlight logic is correct:
`activeArea` initialises to `areas[0].id` and `measure()` re-asserts that as the floor every tick,
`SideRail` clamps `activeIndex` to 0, and the served markup confirms
`class="wsv-rail-item is-active"` + `--wsv-rail-i:0` **on first render**. The pill sits on item 0
from the start.

What is actually missing at that scroll position is **the rail itself** — `railVisible` starts
`false` and only flips once `#wsv-projects`' bottom clears the viewport middle. Since `.wsv-nav`
carries the entire area break as `padding-bottom: $wsv-gap-area` (now 320px), the rail materialises
close to area 1, which reads as "no highlight until area 1".

**Deliberately not changed** — the gate is there because the user asked for it explicitly
("make nav sidebar appear after the carousel directly and disappear above it"). Reversing that
silently would trade one complaint for another. Raised with the user instead.

**One genuine defect found and fixed**: `--wsv-rail-slot` divided by 4 without accounting for the
rail's 1px border. Bootstrap sets `box-sizing: border-box` globally, so `--wsv-rail-h: 340px`
includes both borders — the slot computed 82px while the real flex items are 81.5px. The drift
accumulated down the rail and pushed the pill ~2px past the last item (hidden by `overflow: hidden`).
Border is now a `--wsv-rail-border` custom property, subtracted in the slot formula and used by the
`border` shorthand, so the two can no longer disagree.

### 2. `.wsv-nav-card` — navy shadow
They had a hairline border and **no resting shadow at all**, so they read as flat outlines beside the
embossed cards further down. Added a wide, soft, low-alpha navy lift — the same hue as `.wsv-rail`'s
and `.wsv-plan`'s shadows — with a deeper version of the *same* recipe on hover, so the hover reads
as the card rising rather than as a different shadow being swapped in.

### 3. Alternating area bands
`.wsv-area` / `.wsv-area.is-alt` / `.wsv-area-inner`. Neutral white ↔ `$wsv-band`: both are already
the page's grounds, so this adds structure without introducing a colour the design has to answer for.
`ai % 2 === 1` takes the tint — index 0 is `type-2`, which follows `.wsv-plans` (`$wsv-band`), so it
takes white and the alternation runs from there without two bands touching.

Two structural changes this required:
- **The area gap is now padding, not margin.** A margin falls outside the band and would have opened
  a stripe of page background between every pair of areas. Half the gap comes from the area above,
  half from below; area 1's inline `marginBottom` was halved to match, so every boundary is still one
  `$wsv-gap-area`.
- **`<main>` lost its `maxWidth: 1140` cap**, which moved down to `.wsv-area-inner`. Without that the
  band would have been a 1140px stripe rather than reaching the viewport edges.
- The wireframe `borderTop: "3px solid #555"` was removed — the band now does that job, and the two
  together looked crude. Easy to restore if it is still wanted as scaffolding.

### 4. Jump blur
`is-jumping` on `<html>`, set in `useSectionSnap`'s existing `lock()`/`unlock()` lifecycle alongside
`wsv-snap-off`, driving `filter: blur(2px)` with a 0.16s ease-out.

**The filter is on the sections, not on a wrapper** — and that is the whole design. `filter` makes an
element the containing block for `position: fixed` descendants, so blurring an ancestor of the page
would tear `.navbar-area` (z-index 1030) and `.wsv-rail` (z-index 50) off the viewport and make them
scroll with the content; it would also force a ~9000px-tall layer to rasterize. Sections contain
nothing fixed and only the one or two on screen ever rasterize. The chrome therefore stays sharp for
free — which is the requested effect anyway: HUD crisp, world smeared.
Off under `prefers-reduced-motion`. If it costs frames, the fallback is an opacity/scale dip
(compositor-only) and that is a one-rule swap.

### Verification
`/services/` 200; clean `npx sass`; `.wsv-area`, `.wsv-area-inner`, `is-jumping` and
`--wsv-rail-border` all present in the compiled CSS; three area wrappers render with the expected
white / `is-alt` / white alternation; the old grey `3px solid #555` is gone from the markup; no new
dev-server errors. Feel of the blur and the bands is with the user.

## /services — bigger area gap, shorter nav cards, scroll progress bar

### 1. Area gap widened
`$wsv-gap-area` `clamp(170px, 21vw, 320px)` → **`clamp(240px, 30vw, 460px)`**. This is `.wsv-area`'s
`margin-bottom`, so every area boundary on the page grew together — consistent with the earlier
decision that the whole rhythm moves together, not one boundary in isolation.

### 2. Nav boxes shorter
`.wsv-nav-card`: `min-height` 240px → 176px, padding 34/30 → 24/26. `.wsv-nav-icon`: 54px → 44px,
`margin-bottom` 20 → 14. `.wsv-nav-arrow` `padding-top` 18 → 12. `h3` `margin-bottom` 10 → 6. The
767px override already drops to `min-height: 0` (content-driven on the single-column mobile layout)
with padding already below the new desktop value, so it needed no change.

### 3. Scroll progress bar — new component
`components/Services/ScrollProgress.js` + `.wsv-progress` / `.wsv-progress-fill`. A thin cyan fill
tracking `window.scrollY / (scrollHeight - clientHeight)`, pinned just under the fixed navbar rather
than at the very top of the viewport — y:0 would overlap the logo/nav links since the navbar owns
that band. `top` is measured live off the real navbar via `getBoundingClientRect()` + a
`ResizeObserver`, because the navbar's height changes 5px when it gains `.is-sticky`; a hard-coded
offset would leave a visible gap or overlap depending on scroll position.

**Deliberately not desktop-gated or area-aware**, unlike the rail and the snap hook — it reads
whole-document scroll and stays meaningful on a phone, where the rail is hidden and there is no snap.
`z-index: 1000`, under the navbar's `1030` for the same reason `.wsv-rail` stays under it: must never
float above an open dropdown.

### Verification

compiled CSS; new gap/card values present; no new dev-server errors. Feel of the gap size and the

## /services — snap granularity: one stop per area, not per section

### The visible-gap complaint
"where are the spaces between areas" was diagnosed correctly last pass — the margin (240-460px)
was genuinely rendering, but the area tints (6/5/11/9% mixes) landed within ~15/255 of the page's
own white, so the white GAP and the near-white AREA were nearly the same colour. Confirmed with the
user this pass: the fix (14/12/20/16%) resolved it, and the reference image was shorthand for "make
it visible," not a request to rework areas into bordered/inset cards. No further visual change made.

### Snap granularity — the actual new request
Previously every section was its own snap stop: hero, carousel, navigator, then overview, then
packages, then each of the 3 wireframe blocks per area — 14 stops total, so moving through a single
area was itself a series of jumps. The user wants **one stop per service area**: plain scroll while
inside an area, the jump only when crossing into the next one.

`components/Services/useSectionSnap.js` — `SNAP_SELECTOR` swapped `.wsv-about` / `.wsv-plans` for
`.wsv-area`. This one change is sufficient on its own: the hook's existing "scroll through, then
jump" rule already lets native scroll proceed while a stop's bottom is still off-screen, so an
over-tall stop was always handled — it simply never had a stop bigger than one section to apply it
to before. Making the STOP itself the whole area is what turns that into "normal scroll inside,
jump between areas," with no new logic.

`pages/services/index.js` — removed the `.wsv-snap-stop` marker from the three wireframe `<section>`
blocks per area (9 removed); left on the hero wrapper, which still snaps individually alongside the
carousel and navigator — none of those three are "areas" and weren't part of the complaint.

### Verification
`/services/` 200; served markup shows exactly 1 `.wsv-snap-stop` (hero) and 4 `.wsv-area` elements;
clean compile, no new dev-server errors. Feel of "normal scroll within an area" is with the user.
