### Fix — marquee left a large empty gap (reported by the user, same day)

The projects marquee ran with roughly a third of the strip empty on the right. Cause: **`<html>` is
`dir="rtl"`, so a `width: max-content` flex track is laid out from the container's RIGHT edge and
overflows LEFT.** Its right edge starts flush with the container's, so there is nothing further
right to scroll in — `translateX(-50%)` then drags that edge leftward and empties the right half.

Fix: `direction: ltr` on the track (items are images, so nothing needs the direction back), and the
item spacing changed from `margin-inline-end` to **physical `margin-right`**, since under the track's
forced ltr that is the flow end.

**This was already solved and documented in this codebase.** `styles/style.scss` → `.app-marquee-track`
carries the full account, written when `components/AppDev/TechMarquee.js` hit the identical bug. The
earlier entry above claimed the animation was "direction-independent because a transform" — that is
wrong; the transform is direction-independent but the *track's layout origin* is not. Reading
TechMarquee's JS without its stylesheet is what missed it. **When reusing a technique here, read its
CSS too — that is where the hard-won reasoning lives in this project.**

### Fix, take 2 — the first marquee fix was incomplete

The gap came back. The first fix put `direction: ltr` on the **track**, copying
`.app-marquee-track` from `styles/style.scss`. That was the wrong half of the rule.

**`direction` on a shrink-to-fit box does not decide where that box sits.** The track is
`width: max-content`; which edge it aligns to, and therefore which way it overflows, is decided by
its **containing block's** direction. Setting ltr on the track only reordered the items inside it —
the box itself stayed flush against the RTL wrapper's right edge, still overflowed left, and
`translateX(-50%)` still dragged it off leftward leaving the right side empty. Same symptom, so it
looked like the fix had simply not applied.

Correct fix: **`direction: ltr` on the WRAPPER** (`.hp-marquee`), which makes it an LTR containing
block, so the track starts at the left edge and overflows right — what the keyframe assumes. Safe
here because the strip holds only images, no Arabic text.

Also hardened while in there: **two copies is not always enough.** The track is N copies and the
keyframe advances exactly one, so at the end of a cycle the visible window is
`[1 copy, 1 copy + viewport]` and that must still land inside N copies. One copy is 6 × 420px =
2520px, so at N=2 any viewport wider than 2520px runs off the end and shows empty strip — the same
bug at a different screen size. Now **N=3** (`COPIES`), advancing `calc(-100% / 3)`, which covers
viewports to 5040px. `aria-hidden`/empty-alt updated from `copy === 1` to `copy > 0` so the two
duplicate copies stay silent: 18 figures, 12 hidden.

Third time today a **backtick inside a CSS comment** broke the build (`direction: ltr` in prose).
An audit loop over every `<style jsx>` block in `components/HpNew/` and `pages/hp-new.js` is now
part of the check before serving.

### 🔴 Root-cause fix — styled-jsx never styled ANY `<Link>` in components/HpNew/

The user asked why the nav logo changed, why things were blue, why they looked bad, and why the
support button changed. Three of those were one bug.

**styled-jsx adds its scope class only to DOM elements it renders ITSELF, never to a component.**
Proof from the served HTML:

```
<figure class="jsx-ad8091fe74e3a4ab hp-marquee-item">   <- DOM element: scoped
<a class="hp-hero-btn" href="/website-order/">          <- next/link: NO jsx- class
```

So every rule written as `.hp-hero-btn { }` compiled to `.hp-hero-btn.jsx-hash` and **could never
match**. The links fell back to Bootstrap's `--bs-link-color: #0d6efd` — the blue on screen.

**This had been true since the first structure pass, unnoticed, in four components:** the hero CTA,
both brief buttons, all three plan CTAs, and every nav link. Everything looked "designed" in the code
and rendered as bare blue Bootstrap links in the browser.

Fix: anchor each rule on its scoped **parent** (a real DOM element, so it keeps the `jsx-` class) and
wrap the Link-rendered target in `:global()` — `.hp-hero-text :global(.hp-hero-btn) { }`. Scoping is
preserved by the parent, so nothing leaks. Verified in the compiled CSS: the parent carries the hash,
the target does not.

### The stage — and the constraint that shaped it

The brief: "instead of figure like a phone no its a real phone … it can rotate and get turn like in
app dev page".

**`components/AppDev/AppOrbit.js` can spin its ring a full 360 because its phones are DRAWN** — each
is a flat plane that can face any direction. The real asset,
`public/images/mobile-app/app-mockup.png`, is a photographic render with its 3/4 perspective baked
in; turned side-on it reads as a paper sliver. Checked for alternate angles first — the other files
in `public/images/mobile-app/` are laptop+phone scenes, not other views of the same phone. So there
is exactly one angle. (The render IS a genuine transparent cut-out — corner alpha is 0; the black
seen in an image viewer is just its backdrop.)

Presented the trade to the user, who chose: **real render in front, tilting; CSS phones orbiting
behind.** Implemented so **one gesture drives both** — the same drag feeds the ring (free, with an
inertia throw) and the render (clamped to ±15°, at 0.12 of the ring's rate), so the stage reads as a
single object rather than two things moving near each other.

Mechanics lifted from `AppOrbit.js` — scroll-linked base rotation, hand-tracked velocity, inertia on
release, `backface-visibility: hidden` so the far half of the ring never shows mirrored. Its comments
explain why velocity is measured by hand and why drag ADDS to scroll instead of replacing it; read
that file before changing any of it.

Two deliberate departures:
- **The render answers to drag only, never to scroll.** A phone slowly rotating on its own as the
  page moved would look like it was drifting; the ring behind it is obviously a carousel and reads
  correctly either way.
- **A hovering pointer leans the render on its X axis only** (±5°), so the hover affordance cannot
  fight the horizontal drag.

The whole stage is `aria-hidden` — the drawn phones repeat capability names already in the list
above, and the render is a product shot. Verified in the output.

### App section, take 2 — the phone now genuinely turns 360

"i want the phone 2 turn 3d stuff." The tilt-within-a-range version was not it.

**Fix: the render stopped being the object and became one FACE of an object.**
`.hp-app-slab` is a real 3D box — the photo on the front, CSS side rails for thickness, and a drawn
glass back with a camera module. It turns front → edge-on rails at 90° → back → round again. The
baked-in perspective stops being the limit once the thing has actual geometry.

Parked at `PHONE_REST = -20°` so the slab's geometry agrees with the ~3/4 perspective already in the
pixels; at a true 0° the phone looked turned even though the geometry said face-on. Turns at 0.7 of
the ring's rate so the two do not look glued.

**New derived asset: `public/images/mobile-app/app-mockup-phone.png`** (606×1164, cropped from
`app-mockup.png` at x213-819 / y189-1353). Those bounds were found by scanning the alpha channel for
contiguous opaque column runs, which came back as three: badge 29-197, phone 213-819, badge 823-990.
The original has floating Android and iOS badges either side — on a rotating slab they would swing
around with it, so they are cropped out. **The badges are therefore no longer shown; add them back as
static elements beside the stage if they are wanted.**

Two things that would have broken it:
- **`filter` flattens `preserve-3d`.** The first version had `filter: drop-shadow()` on the render.
  A filter creates a containing block and forces the whole preserve-3d subtree to flatten, so the
  slab would have collapsed into a flat picture. The ground shadow is now a SIBLING span with its own
  blur, never a filter on the slab.
- **`backface-visibility: hidden` on both faces**, or front and back bleed through each other mid-turn.

The camera module uses PHYSICAL `left`, not a logical property: it is a fixed point on an object, not
text that should flip with document direction.
