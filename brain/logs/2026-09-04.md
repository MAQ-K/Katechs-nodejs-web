## `.gitignore` corruption re-investigated and resolved (Known Issue #2)

User ran `git add . && git commit && git push` in `Web/Backup/ar` — against the standing rule,
since Known Issue #2 warned a corrupted `.gitignore` line could let that command commit the live
SendGrid key in `sendgrid.env`. Checked immediately: `sendgrid.env` doesn't currently exist on
disk, so nothing new leaked from that push. But the underlying claim was worth re-verifying
properly rather than just noting the near-miss.

**Finding: the corruption claim was stale.** `.gitignore` has two independently valid, working
rules for `sendgrid.env` — `sendgrid.env` (exact match, line 2) and `*.env` (wildcard, line 3),
both plain ASCII, both verified with `grep -a` reading the file as forced text. `file` reported
the whole file as binary "data" only because of a harmless corrupted line appended at the very
end: null bytes between every character, and even stripped of those it reads "buildsendgrid.env"
— not even the right filename, so it was never a functioning ignore rule to begin with, working
or broken. Confirmed with a hex dump before touching anything.

**Fixed:** truncated `.gitignore` at the exact byte offset (1234 of 1268 bytes) to drop the
corrupted tail. The two real rules are untouched — `file .gitignore` now reports `ASCII text`.

**Still real, still open:** Known Issue #1 — the SendGrid key hardcoded in `pages/api/contact.js`
and `pages/api/web.js`, committed to git history already, independent of this. That's the actual

### 🔴 Sub-navbar pills did nothing — root cause found by driving a real browser

Reported as "subnavbar dont work"; the symptom was **clicking a pill does nothing at all**.

Static checking cleared everything — markup, compiled CSS, `pointer-events`, hit-testing, no
duplicate ids, correct wiring. So a **minimal Chrome DevTools Protocol client was written**
(scratchpad `cdp.js` — ~150 lines, no deps: Node 20 has no global WebSocket and `ws` is not
installed, so it hand-rolls the RFC 6455 handshake and framing) and the page was driven for real.

**Case A** — click with no prior wheel: works, scrolls 1052px.
**Case B** — wheel, then click during the glide: overridden, lands short.
**Case C** — wheel, wait 2.5s for it to settle, then click: **moved 0.** The user's symptom.

Then `window.scrollTo` was monkey-patched to log every caller. The trace is unambiguous:

```
{ top: 3000, behavior: "smooth" }   <- our jump
{ top: 991, behavior: "instant" }   <- write() @ useSmoothScroll.js:100
{ top: 991, behavior: "instant" }   <- ...and again, ~60x a second, forever
```

**`useSmoothScroll`'s rAF loop never terminates.** `step()` stops only when
`|target.current - window.scrollY| < 0.4`, but the browser quantises `window.scrollY`, so a
fractional target is never reached, the loop keeps writing the SAME position every frame with
`behavior:"instant"`, and that cancels any native smooth scroll on its first frame. It also
self-perpetuates: each `write()` sets `wrote.current`, so the hook's own `onScroll` sees the
resulting event as "ours" and never calls `stop()`.

Net effect, sitewide: **after a single wheel event, `window.scrollTo({behavior:"smooth"})` is dead
on every page this hook is mounted on** — which is every page.

**`components/Shared/GoTop.js` already knew.** Its header says the smooth scrollTo "stopped working
the moment the sliding scroll shipped" and it was rewritten around it. `pages/hp-new.js` carried a
comment of mine asserting the opposite — that an explicit `behavior:"smooth"` still animates. **That
was wrong** and is now corrected in the file.

### Fix — the documented pattern, not a workaround

`/hp-new` now owns its scroll like `/services` does:
- `pages/_app.js`: `pageOwnsScroll` is now `/services` **or** `/hp-new`, so `SmoothScrollGlobal` is
  left out and exactly one instance stays live.
- `pages/hp-new.js` mounts `useSmoothScroll()` itself (snap:false — push-to-cross stays exclusive to
  `/services`) and the navigator jumps through **`scrollToY`**, never `window.scrollTo`.

### ⚠️ Left alone deliberately — the underlying hook bug

The non-terminating loop in `components/Services/useSmoothScroll.js` is **still there**. It is a
shared file mounted on every page, and fixing its termination condition would change scroll
behaviour sitewide — that deserves the user's call, not a side effect of a homepage fix. Cost of
leaving it: native smooth scrolling stays dead everywhere, and a `scrollTo` fires every frame
forever after any wheel input (a real, if small, performance cost). **Anything else that needs a
programmatic scroll must use `scrollToY`, not `window.scrollTo`.**

### The trap: AppOrbit is only styled inside `.app-platforms`

Every one of AppOrbit's rules in `styles/style.scss` is **nested inside `.app-platforms`**
(line 9327), so rendering `<AppOrbit />` anywhere else produces completely unstyled markup. The
wrapper must carry that class.

But `.app-platforms` is *also* a section-level rule at **styles/style.scss:7859** — navy background,
100px top and bottom padding, overflow hidden. That is section chrome, not orbit styling. So the host
is `.app-platforms .hp-app-orbit-host` and the second class cancels the background and padding; two
classes beat one, so no `!important`.

Anyone reusing an `AppDev`, `Seo` or `DigitalMarketing` component elsewhere should check for the same
thing first — these SCSS blocks are namespaced under a page-level class, and the component alone is
not portable.

This is the **second** documented exception to the `components/HpNew/` no-`style.scss` rule, after
`.default-btn` in `HeroNav.js`. Both are now listed in `components/HpNew/README.md`.
