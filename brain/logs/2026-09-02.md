### 2. Service navigator — picking a service now glides instead of teleporting

`components/Services/ServiceNav.js` gained an optional `onNavigate(id)`; the page passes its own
`scrollTo`, the same one the SideRail uses.

**Why the cards did nothing visible before:** they were plain `#hash` anchors, and `useSmoothScroll`
adds `.wsv-smooth` to `<html>` to kill Bootstrap's `:root { scroll-behavior: smooth }` for the whole

Without `onNavigate` the component stays a plain anchor — crawlers, middle-click and modified clicks

block you asked for, and from the top edge every area looks alike. Class is removed then re-added
with a forced reflow between, so choosing the same area twice replays it. `prefers-reduced-motion`
kills it. Timer cleared on unmount.

### 3. Areas float on a dark ground

`.wsv-areas` (new wrapper in `pages/services/index.js`), `$wsv-space: #060c4a` — same navy as
`.navbar-navy`, so header and space frame the page together.

The gaps between areas were plain white page, which read as "nothing here yet" rather than as
deliberate space. Dark blue turns the same distance into a backdrop and the areas become lit slabs on
top of it — `border-radius: 18px` plus two shadows: a long lower drop (the slab's weight) and a short
upper counter-shadow so the top edge separates too. Both use negative spread so they stay off the
left/right edges, where a full-bleed area has no visible border to cast from.

**`.wsv-nav`'s `margin-bottom` moved to `.wsv-areas`' `padding-top`** — same distance, but now it is

### Two traps avoided (worth keeping in mind before touching this wrapper)

- **`.wsv-areas` must stay unpositioned and must never get a `transform` or `filter`.** `.navbar-area`,
  `.wsv-rail` and `.wsv-progress` are `position: fixed` inside this subtree; any of those properties
  would make the wrapper their containing block and tear them off the viewport.
- The page's scroll-spy read area tops with **`el.offsetTop`**, which is measured from the nearest
  *positioned* ancestor. Adding any wrapper with `position: relative` would have silently shifted
  every reading while `useSmoothScroll` (which already used `getBoundingClientRect`) carried on
  agreeing with the viewport — the two would have picked different "current" areas. Switched the spy
  to `getBoundingClientRect().top + scrollY` so the two now measure identically by construction.

### Follow-up 3 — area elevation made firm (user: "more firm / reduce blur / modern")

`0 -14px 28px -20px` + `0 34px 60px -26px` → three layers:


## Sitewide font → Almarai

User: "use Almarai from google fonts for the whole website pages."

### What it replaced
FOUR families were being fetched in `pages/_document.js` and two were live:
- `$body-font-family` / `$heading-font-family` = **Droid Arabic Kufi** (also pulled a second time by a
  CSS `@import` at the top of `style.scss`)
- **Cairo**, opted into by hand in **116** places (115 `font-family` rules + the `--ds-font` token)
- **Open Sans** and **Dosis** were fetched but their `$…-font-family` assignments were commented out,
  so they had been dead weight on every page load for some time.

All four `<link>`s are gone. One Almarai link remains, with `preconnect` to both googleapis.com and

without it opens a connection the font request cannot reuse).

The `@import url(droidarabickufi)` inside `style.scss` was deleted rather than swapped. A CSS
`@import` in the main stylesheet is only discovered after that stylesheet has downloaded and parsed,
so it serialises two round trips before any text can paint. The `<link>` does not.

### Structure
New `$font-family: "Almarai", sans-serif;`, with `$body-font-family` and `$heading-font-family` both
pointing at it — kept as separate names because ~13 rules reference them and because giving headings
their own face later should stay a one-line change. All 116 Cairo stacks now say `$font-family`.
`--ds-font: #{$font-family}`.

styled-jsx cannot see Sass variables, so the 11 component/lab files that carried a literal Cairo
stack were rewritten to the Almarai literal (`components/Sections/`, `components/Motion/`,
`components/AnimeJs/`, `pages/lab/`).

Compiled result: 128 × `font-family: "Almarai", sans-serif`, 24 × `var(--ds-font)` (which is
Almarai), 1 × `"boxicons"` (the icon font, untouched).

### ⚠️ Weight availability — read before editing type
**Almarai ships FOUR weights and no others: 300, 400, 700, 800.** Requesting 500 or 600 from Google
Fonts returns **HTTP 400** — verified, not assumed. The stylesheet still writes:

- `font-weight: 600` in ~82 places → CSS font matching resolves these to **700**
- `font-weight: 500` in ~19 places → resolves to **400**

So roughly a hundred rules render at a weight they do not name. Nothing is broken and no synthetic
bolding occurs, but semibold text across the site is now noticeably heavier and medium text lighter
than under Cairo, which had 500/600 available. If that reads wrong anywhere, the fix is to change the
`font-weight` values — NOT to add 500/600 to the `<link>`, which cannot work.

Warning recorded at the `$font-family` declaration in `style.scss` and in the `_document.js` comment.

Several comments asserted the opposite of the new truth ("the sitewide heading font stays Droid
Arabic Kufi"). Updated in `style.scss` (×4), `HeroBuildSmarter.js` and — importantly —

### 2. Back-to-top button fixed
`components/Shared/GoTop.js` rewritten (class → function).

**What was wrong:** `scrollToTop()` was `window.scrollTo({ top: 0, behavior: "smooth" })`. The smooth
-scroll hook puts `wsv-smooth` on `<html>`, which sets `scroll-behavior: auto` — it has to, because
bootstrap.min.css sets `:root { scroll-behavior: smooth }` and leaving that on makes every frame of
the glide start its own animation. With the override live, `behavior: "smooth"` is ignored and the
button **teleported** instead of travelling. Item 3 below put the glide on every page, so this would
have gone from a /services bug to a sitewide one.

It now animates itself on rAF with the same easing family and `behavior: "instant"` writes. Also
fixed while in there: the `scroll` listener was never removed, `setState` fired on every scroll tick
rather than only when visibility flips, and the control was a `<div onClick>` — unreachable by
keyboard and invisible to a screen reader. It is a real `<button>` with an aria-label now, which
needed `border/padding/appearance` resets in the `.scroll-to-top .top` rule or the UA button chrome
paints over it. A wheel or touch during the climb cancels it.

### 3. Sliding scroll on every page — the slide, not the mechanism
`useSmoothScroll()` now takes `{ snap = false }`. `snap` gates `canSnap`, which is the entire
area-to-area push-to-cross mechanic; with it false the wheel handler skips that block and only the
glide runs.

- `components/Shared/SmoothScrollGlobal.js` (new) — calls the hook with defaults, renders null.
- `pages/_app.js` mounts it, **except** when `router.pathname === "/services"`.
- `pages/services/index.js` opts in with `{ snap: true }`.

**Exactly one instance may be live.** Two would both `preventDefault` the same wheel event and both
write `window.scrollTo`, fighting each other every frame — hence the route guard, and hence the
wrapper component (a hook cannot be called conditionally). `pathname`, not `asPath`: asPath carries
the trailing slash and any `#hash` and would stop matching on a deep link.

### How it was done

**Selector depth is load-bearing.** Each page's rules are nested two or three classes deep

would lose on specificity, so every selector in the block MATCHES its page's depth and wins on source
order. Shortening them, or moving the block earlier in the file, silently breaks it. Noted in the
block header.

(20px/700), supporting line, price hairline, tick wells, CTA.

### Two judgement calls worth flagging
1. **The badge is cyan-on-navy, not `.wsv-plan`'s navy-on-white.** This is the one deliberate
   departure from the chosen reference, and it fixes a real bug: `.wsv-plan.is-popular` never
   restyled its badge, so on the recommended card it was navy on navy — **invisible**. It had the
   same defect in its earlier black-on-black form, so this is long-standing, not something today
   introduced. Cyan reads on both grounds and is what seo/dm/tr and email already used.
2. **Hosting's CTA moved below its feature list via flex `order`**, not by editing JSX, since the
   scope rules that out. A screen reader still follows DOM order; acceptable because the button
   keeps its label and stays reachable, it is only relocated visually. If the JSX is ever touched,
   move the element and drop the `order` rules.

### Not unified, on purpose

- **seo/dm/tr show their badge only on the popular card** (`display: none` by default). That is an

### The 767px trap
`.wsv-plan` tightens to `26px 22px` on phones in the `.wsv-*` responsive group. Adding the other five
selectors to *that* rule would not have worked: **a media query adds no specificity**, so section 1
of the new block, being later in the file, beats it. The parity rule therefore lives at the end of
the new block in its own `@media`.

The working version strips comments first and tracks brace depth.

## Three page fixes: marquee loop, SEO audit bar + plans FAB, DM hero order

### 1. `/services/app-development` — the tech marquee never looped

**Cause was RTL, not the animation.** `<html>` is `dir="rtl"`, so a `width: max-content`
flex track is laid out from its container's RIGHT edge and overflows to the LEFT. Its right edge
therefore starts flush with the container's, and there is nothing further right to scroll in.
`translateX(-50%)` then drags that right edge leftward and leaves the right half of the strip empty —
items marched off to the left and never came back round, exactly as reported. The doubled item list
and the `-50%` keyframe were both correct all along; the layout direction was not.

Fix: `direction: ltr` on `.app-marquee-track` so it overflows rightward, with `direction: rtl` set
back on `.app-marquee-item` so the Arabic labels ("إشعارات فورية", "بوابات دفع") keep their icon on
the correct side. Only the track's ORDER needs to be LTR, not the text.

**Second, smaller bug found while in there:** `gap: 12px` on the track applied BETWEEN the two copies
as well as inside them. 20 items give 19 gaps, so `-50%` came up half a gap (6px) short and the loop
stuttered every cycle. Replaced with `margin-right: 12px` on every item, making each copy exactly
`10 × (item + 12)` so half the track lands on the seam. Physical `right` deliberately: the track is
`direction: ltr`, so right is the flow end there — a logical `margin-inline-end` would resolve
against the item's own `rtl`, land on the left, and indent the head of the track (same total width,
so the loop would still be seamless — just uglier).

### 2. `/services/seo` — the free-audit form

**`.seo-audit-bar`, `.seo-audit-bar-field`, `.seo-audit-bar-submit` and `.seo-audit-bar-error` had
ZERO styles.** Not in `style.scss`, not in bootstrap. `components/Seo/AuditForm.js` shipped
referencing them, so the section rendered as three raw browser controls on the dark band. That is the

## Emails popular plan card — the cyan wedge (user screenshot)

The recommended card on `/services/emails` rendered narrower than its neighbour, with a large cyan
wedge filling the space beside it instead of the intended 2px rotating ring.

**Root cause, and it is not the ring.** `components/Emails/BorderBeam.js` wraps the card in
`.email-beam-panel`, which is `display: flex` — so the card is a flex ITEM. `.email-plan-card`
declared neither `width` nor `flex`, so it shrink-wrapped to its content and left a wide empty strip
inside the wrapper. The spinning conic-gradient sits at `z-index: -1` behind that wrapper, so the
strip did not render as empty: it rendered as the gradient.

**Both other pages with this ring already handled it** — `.app-plan-card` declares `width: 100%` on
itself, and `.hosting-pricing-beam .hosting-pricing-card` declares it in the beam rule. Emails was
the one page that never did. Pre-existing, not introduced by the plan-card unification, but it made
the unified look obviously wrong on that card, which is how it surfaced.

Fix: `width: 100%` on `.email-plan-beam .email-plan-card`.

### Two dead things removed while in there
`BorderBeam.js` puts BOTH `email-beam-panel` and `email-plan-beam` on one element, and this file had
grown a **complete ring implementation for each** — two `position/overflow/padding/radius` sets and
two `&::before` rules competing for the same pseudo-element, with `.email-beam-panel` winning on
